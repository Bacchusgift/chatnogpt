# 插件设计定位

> 核心特色：**伪装成 GPT**——这是产品的灵魂，一切实现不得妥协。
> 其余一切：**插件化**——社区可贡献不同类型的插件来提高娱乐性。

## 定位与取舍

插件是**轻量的、可插拔的、可丢弃的娱乐内容**，不是系统级特性。据此：

- ❌ 已废弃：v2 初稿中的 `convs.conv_type` 列、`messages.meta` 列、`PipelineHooks`
  管线钩子——把娱乐插件抬成系统级架构，过度设计，discard。
- ✅ 保留：v2.3.0 已上线的最小体系——
  - 后端：`pluginbase`（Meta 自描述 + Mount 自挂载 + 注册表 + 统一门禁/身份）
  - 前端：事件 hooks（`cngp:conv-opened` / `cngp:message-actions` / `cngp:room-created` /
    `cngp:plugins-loaded` / `cngpRoomModes`）

这个体量已经足够社区写娱乐插件；在第二个社区插件真实需要之前，不再增加任何机制。

## 社区插件的三种典型形态

1. **会话面板型**：监听 `cngp:conv-opened`，在会话内渲染自己的面板
   （例：海龟汤的游戏状态卡）。
2. **消息增强型**：监听 `cngp:message-actions`，给消息操作条追加按钮
   （例：是 / 不是 / 是也不是 / 无关）。
3. **模式贡献型**：`cngpRoomModes.push()` 贡献对话模式 + 监听 `cngp:room-created`
   初始化（例：创建房间时选择海龟汤模式）。

消息收发、历史、伪装、通知——全部走主流程，插件不碰管线。

## 上架要求（社区贡献审核标准）

1. **伪装一致**：消息必须走正常通道（`doSend` / `/send`），不得绕过密文、圆孔、
   打字机、通知伪装。插件 UI 里的秘密（谜底等）只存服务端、按身份裁剪下发。
2. **可丢弃**：停用插件后零残留——不建基座表、不改基座文件；插件自有存储随停用自然失效。
3. **缓存版本化**：脚本 URL 带 `?v=`，内容变更自行 bump。
4. **测试**：插件包自带单测；上线前 `go test ./...` 双后端 + 对应冒烟脚本。

## 面板类插件的正确形态（v2.3.7+）

面板增强类内容**不进消息流**，统一挂到基座右侧抽屉（`CNGP.drawer.setPanel`）：
- 抽屉壳子由基座提供（头部切换按钮、自动展开/收起、移动端全屏覆盖）
- 插件只提供 `{title, render(el, ctx)}`，刷新调 `CNGP.drawer.refresh()`
- 消息流保持纯聊天；面板放游戏状态、进度、配置等"增强层"内容
- 例：海龟汤的谜面/谜底/开局控制全部在抽屉面板内，谜底以伪装块呈现

## 操作条能力覆盖（v2.4.1）

操作条按钮 = 可注册能力（id：copy/refresh/vote-up/vote-down/reply/react）。
插件经 `CNGP.actions.register` 以三种 placement 参与定制：
`append` 追加 / `replace:<id>` 语义改写（位置形态保留）/ `hide:<id>` 隐藏。
冲突规则：同一能力多插件改写时后注册覆盖先注册（控制台告警）。
海龟汤的裁决按钮（是/不是/是也不是/无关）即为该机制的首个使用者：
覆盖点赞/点踩 + 追加两个裁决，点击发引用回复，群成员可感知回应目标。

## 基座侧的唯一义务

保持现有 hook 事件与 `pluginbase` 接口稳定。需要新 hook 时，先出现真实的第二个
使用场景，再抽象通用机制——继续遵守"基座认识 hook，不认识具体插件"。
